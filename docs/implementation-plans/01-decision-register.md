## Resolved Interpretations

| ID | Decision | Rationale |
| --- | --- | --- |
| R1 | `Esc` during transcription enters `Transcribing(Cancelling)` until the matching worker outcome arrives. | This is required by functional spec sections 5 and 16 and architecture sections 6, 16, 17, and ADR-11. It supersedes the contradictory immediate-Ready diagram in architecture section 39. |
| R2 | Every transcription gets a monotonically increasing `TranscriptionId`; every terminal worker event includes it. | Architecture section 7 says IDs are mandatory, and they prevent stale events and cancellation races. |

## Slice 4 Gate Resolutions (D5)

Resolved 2026-08-10 while implementing slice 4. Blocking row D5 is satisfied; the worker protocol tests in `transcriber::tests` cover each terminal outcome with a fake transcriber.

| ID | Resolution | Evidence |
| --- | --- | --- |
| D5 | **Worker lifecycle** (worker lives in `src/transcriber.rs`; plan file `05-worker-transcription-flow.md`):  - **Bounded job protocol**: job channel is `mpsc::sync_channel(1)` — at most one queued job, no backlog. The state machine guarantees the controller never submits while a job is outstanding (it only submits from `Recording` and stays `Transcribing` until the worker's outcome), so `send` never blocks; the bound is the enforcement arm if that invariant is ever violated. A job carries `TranscriptionId`, normalized `RecordedAudio`, and the shared `Arc<AtomicBool>` cancellation flag (architecture section 15, decision R2).
  - **Startup handshake**: `transcriber::spawn_worker` runs a factory on the worker thread (`WhisperTranscriber::new` creates the `WhisperState` from the already-loaded `WhisperContext`) and reports `Result<(), String>` over a one-shot channel before the app becomes Ready. `spawn_worker` blocks on the handshake; `Err` → `ModelError::WorkerStartup` → `main` exits non-zero without entering interactive state. A factory panic or premature worker exit is also a startup failure (recv error), never a hang. Tests inject a fake factory (`Ok`/`Err`).
  - **Submission failure**: worker death drops the job receiver, so `SyncSender::send` returns `SendError` → the controller treats it as a recoverable transcription failure, prints an error, and returns Ready (already implemented in slice 2/3 `finish_recording`; kept).
  - **Panic policy**: per-job `catch_unwind(AssertUnwindSafe(..))` around `transcribe` + text extraction; a panic becomes `TranscriptionFailed` (message includes the panic payload) and the worker stays alive for the next job. Only the outer `recv`/`send` loop is outside the catch; those do not panic, so a panicking job can never strand the controller in `Transcribing`. A worker-thread panic outside a job (not possible today) would drop the job receiver and surface as a submission failure on the next cycle.
  - **Shutdown signal/acknowledgement**: the worker exits its loop when `jobs.recv()` errors (all senders dropped — `main` drops `App`, which owns the only job sender) or when an outcome `events.send` fails (event receiver dropped when `app::run` returns). No dedicated shutdown message is needed; channel closure is the signal. `App::shutdown()` sets the active transcription's cancellation flag so an in-flight inference aborts at the next encode/decode boundary instead of running to completion.
  - **Join timeout**: `WorkerHandle::join_with_timeout(WORKER_JOIN_TIMEOUT = 2 s)` polls `JoinHandle::is_finished` and then joins; on timeout `main` proceeds to exit and process teardown terminates the worker thread (the worker owns the context/state, so no double-free: the thread is killed by the OS).
  - **Repeated Ctrl+C**: the first Ctrl+C (raw-mode key event) returns from `app::run` and starts shutdown; the terminal is restored before the join, so a second Ctrl+C during the ≤2 s shutdown window is a normal SIGINT that kills the process (escape hatch); the join bounds the wait and shutdown never hangs. | Constants/`spawn_worker`/`worker_loop`/`process_job`/`WhisperTranscriber`/`WorkerHandle` in `src/transcriber.rs`; `App::shutdown` in `src/app.rs`; startup wiring in `src/main.rs`; worker protocol tests (one job at a time, outcome classification, panic survival, channel-close exit, join timeout, handshake) in `transcriber::tests`; controller tests (submit-once, event gating) in `app::tests`. `set_abort_callback_safe` signature verified in whisper-rs 0.16.0 `whisper_params.rs`; abort returns `-6`/`-8`/`-9` verified in vendored whisper.cpp 1.8.3 (`whisper.cpp` lines 7020/7146/7458 + `return !(abort_callback && ...)` at 2455/2977); default `print_progress`/`print_timestamps`/`language="en"` verified at `whisper_full_default_params` (line 5906); `detect_language` override verified at line 6812. |

### Slice 6 notes

- **Observed cancellation latency and fallback limits (developer-facing validation notes, plan step 7)** — measured 2026-08-10 on Ubuntu 24.04 with the pinned `ggml-base.bin` and whisper-rs 0.16.0 / vendored whisper.cpp 1.8.3 (default 4 threads; synthetic silent audio; flag set mid-inference via a one-off ignored probe removed before commit, since this machine's audio input cannot capture speech — see Slice 4 notes):
  - 10 s audio: full uncancelled run 1.31 s; with the flag set 200 ms in, `full()` returned an error at 1.28 s (flag→return ≈ 1.08 s; savings ≈ 30 ms — silence produces little decode work).
  - 60 s audio: full uncancelled run 2.62 s; with the flag set 200 ms in, `full()` returned an error at 1.32 s (flag→return ≈ 1.12 s; cancellation saved 1.30 s). whisper.cpp processes audio in ~30 s chunks (`n_audio_ctx` = 1500 frames), and the observed abort always lands right after the current chunk's mel/feature pass.
  - **Fallback limits**: cancellation is cooperative and only observed between graph nodes. The per-chunk log-mel spectrogram (`whisper_pcm_to_mel_with_state`, line 3875, → `log_mel_spectrogram`) is **not** abort-polled (its signature has no callback), so the worst-case flag→abort-return latency is bounded by one chunk's mel computation — observed ≈ 1.1–1.2 s for 30 s chunks on this machine, scaling with CPU speed and chunk length, not with total recording length. The encoder/decoder graphs poll per node, so once the mel is done the abort lands within milliseconds. If native interruption were ever unavailable, the fallback would be `process_job`'s pre/post-inference flag checks only (the flag set before inference starts is honored without running `full`; a flag set mid-inference would not stop the run) — the architecture does not rely on that fallback because the abort callback is verified present (D2).
  - The controller is insensitive to this latency by design: it stays in `Transcribing(Cancelling)` until the matching worker event (R1, ADR-11), renders `Cancelling transcription...` immediately, and rejects `Ctrl+R` and all outcome text meanwhile, so a slow abort never permits a concurrent job or prints a cancelled result.
- Manual pty checks on 2026-08-10 (isolated `XDG_DATA_HOME=/tmp/vs006-xdg` with the seeded verified model, `TERM=xterm script`, timestamped log): a ~15 s real recording finished into `Transcribing...`; `Esc` pressed 0.22 s later rendered `Cancelling transcription...` immediately while cleanup was pending; the worker acknowledgement arrived 1.6 s later and returned to `Ready`; a `Ctrl+R` sent during the Cancelling window was ignored (no render, no new job — covered deterministically by `cancelling_accepts_no_commands`); `Ctrl+R` after the acknowledgement started the next recording normally; `Esc` during `Recording` returned to `Ready` silently. The session log contains zero `Transcription:`/`Copied to clipboard.`/`Error` lines, and the X11 (`DISPLAY=:1`) clipboard read back empty after the run — no cancelled text was ever printed or copied. `Ctrl+C` exited 0 with the terminal restored (cursor `^[[?25l` on entry, `^[[?25h` on exit).

Resolved 2026-08-10 while implementing slice 8. | ID | Resolution | Evidence |

| D6 (line endings) | Raw mode disables the kernel's output post-processing, so a bare `\n` no longer maps to `\r\n` and would move the cursor down without returning it to column zero. `TerminalRenderer` therefore serializes every logical line feed — status-block lines, output lines, embedded newlines, and its own appended terminator — as `\r\n` through a private `write_crlf(&mut impl Write, &str)` helper; `render` delegates to a private `render_to(&mut impl Write, ...)` so byte-level behavior is testable without a TTY (plan step 4). ## Slice 10 Gate Resolution (D7 - fixed terminal UI)

Resolved before implementing slice 10 for issue 22. This supersedes only D6's append-only rendering decision; its input polling, key mapping, runtime-I/O, raw-mode Ctrl+C, and shutdown policies remain unchanged.

| ID | Resolution | Evidence |
| --- | --- | --- |
| D7 | **Rendering policy**: render one bounded complete view in place whenever display state changes. The view contains state-derived status and commands, `latest_transcription: Option<String>`, and `notice: Option<String>`. The controller owns both optional display values: a successful completion replaces `latest_transcription` and sets a copy-success or clipboard-warning notice; recoverable errors replace only `notice`; cancelled and failed recordings/transcriptions do not clear the most recent successful transcription. The terminal boundary alone issues Crossterm cursor/screen commands and serializes logical newlines as CRLF; canonical transcript text reaches the clipboard unchanged. **Redraw strategy**: move to the interface origin, clear the previously occupied view region or the terminal viewport, write the entire current view, and flush as one render operation; no normal transition appends output. **Resize**: resize events are delivered to the application loop and request a redraw of the current view without changing application state. **Failure/cleanup**: terminal write failures still propagate as `TerminalError` to `main`; `TerminalGuard` still restores raw mode and cursor visibility. The fixed interface may leave its final rendered content visible after terminal restoration. | Architecture specification sections 19, 21, and 23; functional specification section 11 and acceptance criterion 20; slice 10 renderer byte-level and controller-view tests; manual acceptance multiple-cycle scenario. |
